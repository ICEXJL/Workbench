# SPEC-011：日报累计销售额自动取数

状态：`implemented`（来源已按用户最新确认改为 `dny_data`；实现与验证结果见当前 TASK/HANDOFF）  
创建日期：2026-09-29  
来源：用户在 `/report/submit` 页面提出的需求；只读仓库与 MySQL 核查

## Overview

日报中的销售额（USD）由服务端从 `dny_data` 自动汇总，乘以 75% 后用于月度目标完成率。销售范围是当前登录账号对应运营在 `dp_ry` 的全部店铺；统计区间为日报月份第一天至日报日期（含）。提交日报时服务端重算、应用 75% 系数并保存金额快照。`fbs_data` 不参与日报金额查询，也不作为缺失店铺的回退来源。

用户已确认 USD、全部映射店铺、不允许手工输入、保留历史快照、零金额有效；源表采用 `dny_data`，以 `rq` 为日期、`xse` 为销售额。计算真实累计销售额时，源表最新日期必须覆盖日报日；未覆盖或没有店铺映射不再阻止日报提交，新日报销售额默认保存为 `0.00`。更新已有日报时若销售额暂不可计算，则保留已保存的销售额快照。`monthly_sales` 保持 `NOT NULL DEFAULT 0.00`，不修改表结构。

## Scope

- 日报提交页的累计销售额展示、加载状态和完成率计算。
- `GET /api/v1/report/daily/mine` 为当前登录用户读取自动计算结果。
- `POST /api/v1/report/daily` 服务端计算并保存日报销售额快照。
- 使用 `operator`、`dp_ry`、`dny_data`、`daily_report` 和 `target_monthly` 现有数据链路。
- 日报列表继续读取 `daily_report.monthly_sales` 中的已提交快照。

## Out of Scope

- 修改或重建 `dny_data` 上游数据同步。
- 自动修复 `dp_ry` 中缺失或错误的店铺归属。
- 回填或重算已提交的历史日报。
- 修改月度目标的配置方式和金额。
- 修改销售总览、人员销售或其 `dny_data` 查询口径。
- 在本需求中新增数据库表；索引/约束调整需另行评估、迁移和回滚。

## User Stories

- **REQ-011**：作为运营人员，我希望日报自动显示我名下店铺本月累计销售额，不再手工输入。
- **REQ-012**：作为运营人员，我希望日报目标进度面板直接使用该自动金额，减少人工核算差错。
- **REQ-013**：作为主管或管理人员，我希望日报记录保留提交时的销售额快照，后续查看时能解释当日报表当时使用的金额。

## Functional Requirements

- **REQ-014**：读取当前日报时，服务端必须依据登录 JWT 中的 `userId` 定位本人，不接受请求参数指定其他运营人员。
- **REQ-015**：服务端必须以当前运营对应的 `dp_ry` 店铺映射关联 `dny_data`，按已确认的月区间汇总销售额。
- **REQ-016**：日报页面不得要求运营手工录入该金额；自动金额应参与现有完成率、缺口和进度状态计算。
- **REQ-017**：提交/更新日报时，服务端不能信任浏览器提交的金额值；提交请求必须先完成日报写入，不得同步等待销售汇总，销售额由响应后的后台任务重新计算并更新 `daily_report.monthly_sales`。
- **REQ-018**：同一运营同一日期重复提交继续更新唯一日报记录；提交时重新计算并保存当时的销售额快照。
- **REQ-019**：未确认业务范围前，不得把 `dp_ry.qy='东南亚'` 或 `dp_ry.fbs='是'` 写成过滤条件。
- **REQ-020**：无店铺映射或源水位未就绪时，日报提交允许先保存默认 `0.00`；销售查询仍需通过独立摘要状态区分这些情况。源数据格式错误和数据库连接失败必须记录为后台刷新错误，不得伪造为已计算金额。
- **REQ-021**：历史日报列表继续使用已保存的 `monthly_sales` 快照；不得自动回填或改写历史值，除非另有批准的迁移需求。
- **REQ-022**：仅当源表全局水位达到或超过日报日时，服务端才可返回可用金额；金额统计截止日为日报日，不得以历史水位金额代替当日完整值。

## Business Rules

- **BR-011**：登录主体以 JWT `userId` 为唯一入口，服务端不得让前端传入 `operator_id` 来决定销售范围。
- **BR-012**：店铺关系为 `operator.real_name = dp_ry.yy` 且 `dp_ry.dpbh = dny_data.dpbh`。读取当前运营在 `dp_ry` 中的全部店铺，不过滤 `qy` 或 `fbs`，并按 `dpbh` 去重。
- **BR-013**：月累计区间为日历月第一天至 `report_date`（含首尾），按 `dny_data.rq` 筛选；不得使用客户端日期替代服务端已校验的日报日期。
- **BR-014**：候选销售额为该运营映射店铺在区间内 `SUM(dny_data.xse)`；`dds` 是订单数量，不作为销售额。
- **BR-015**：页面及接口将 `dny_data.xse` 按 USD 处理（用户确认）；源表没有币种列，上游实际口径仍依赖数据生产方。
- **BR-016**：纳入 `dp_ry` 全部区域及 `fbs` 是/否店铺，不加 `qy` / `fbs` 过滤。
- **BR-017**：提交时保存到 `daily_report.monthly_sales` 的金额是快照。历史日报列表继续读取快照，不随 `dny_data` 后续变化自动重算。
- **BR-018**：以 `dny_data` 全表 `MAX(rq)` 作为同步水位。只有水位达到或超过日报日时才按月初至日报日汇总；水位早于日报日时 GET 返回 `not_ready`，POST 允许提交，首次提交销售额保存为 `0.00`，更新已有日报则保留原销售额快照。当前源表是稀疏日表，不能将单店缺少某日行单独认定为延迟。
- **BR-019**：没有 `dp_ry` 映射时 GET 返回 `mapping_missing`；POST 允许提交，首次提交销售额保存为 `0.00`，更新已有日报则保留原销售额快照；不提供人工金额入口。
- **BR-020**：金额按两位小数保存到已有 `DECIMAL(18,2)` 字段；源列是字符串，转换失败不得静默转成 0，应返回错误并阻止提交。
- **BR-021**：金额为 0 是有效值；当源表水位已覆盖本次有效统计区间且运营在区间内无销售行时，累计额返回 `0.00`。
- **BR-022**：`period_end` 必须是本次金额实际覆盖的最后日期，即 `min(report_date, MAX(dny_data.rq))`；若该日期早于当月第一天，不展示金额，避免返回倒置统计区间。
- **BR-023**：日报累计金额 = 全部映射店铺月累计 `SUM(xse) * 0.75`，先应用系数再按 `ROUND_HALF_UP` 四舍五入到 USD 美分；接口实时金额、目标进度分子及新提交的 `monthly_sales` 快照必须使用该同一结果。历史快照不回填、不追溯调整。

## Data Model

以下为 2026-09-29 对当前配置 MySQL 的只读观察，不是表结构变更或持续性数据保证。

| 表 | 已观察字段/约束 | 本需求用途与注意事项 |
| --- | --- | --- |
| `dny_data` | `dpbh`、`dds`、`xse`、`ckh`、`rq` 为 `VARCHAR NOT NULL`；存在非唯一索引 `idx_dny_rq_dpbh` | 日报销售额事实来源。只读观察：全表 209,862 行、1,499 个店铺编号，`MAX(rq)=2026-09-30`；朱文剑映射的 15 个店铺均在该表有记录。`rq`/`xse` 是字符串，解析失败必须报错；没有币种列，日报展示 USD 是业务确认，不是表结构属性。索引不保证同店同日唯一。 |
| `dp_ry` | `dpbh`、`yy`、`qy`、`fbs` 等为 `VARCHAR(255) NOT NULL`；未发现索引、主键或唯一约束 | 通过 `yy` 映射运营、通过 `dpbh` 映射店铺。当前 1,477 行/1,477 个不同店铺编号，无重复店铺键。启用 `operator` 中有 3 人没有 `dp_ry` 映射。 |
| `operator` | `id` 主键、`real_name` 唯一、`role`、`status` | 从 JWT 对应用户 ID 取得标准运营姓名，禁止以客户端姓名确定主体。 |
| `daily_report` | `monthly_sales DECIMAL(18,2)`；存在 `(operator_id, report_date)` 唯一索引 | 保存日报提交时销售额快照；现有 `cumulative_sales` API 字段由 `monthly_sales` 别名提供。 |
| `target_monthly` | 按 `(operator_id, month)` 唯一索引，含 `sales_target` | 维持现有目标读取和完成率分母。 |

现有前端/API 名 `cumulative_sales` 继续用于兼容，与物理字段 `daily_report.monthly_sales` 对应；它不是数据库中的独立列。源金额先由服务端汇总，再按两位小数写入该快照字段。

当月 SQL 观察：截至 2026-09-30，朱文剑（`operator.id=89`）在 `dp_ry` 有 15 个店铺映射，9 月对应 434 个店铺-日期组合；`Shopee-PH90(三仓)` 在 `dny_data` 有 2026-09-01 至 2026-09-30 共 30 行，`SUM(xse)=1518.68`，而在 `fbs_data` 无该店记录。该观察用于验证本次来源选择，不代表所有运营/月份的源数据都完整。

## API Contract

- **API-011**：继续使用受 JWT 保护的 `GET /api/v1/report/daily/mine?report_date=YYYY-MM-DD`；日报主体必须取自 JWT。现有 `report`、`target`、`identity` 响应保持兼容。
- **API-012**：GET 响应增加 `sales_summary`，包含应用 75% 系数并按美分舍入后的 `amount`（JSON 数值或 null）、`currency`、`period_start`、`period_end`、`data_as_of`、`source` 和 `status`。不得返回其他运营人的店铺或销售额。
- **API-013**：`POST /api/v1/report/daily` 的日期、角色、周度字段和店铺波动校验保持现状；接口先保存新日报默认金额或已有快照，销售额再由后台任务基于 JWT 主体和 `report_date` 重算并更新。
- **API-014**：请求中的 `cumulative_sales` 改为可选兼容字段；旧客户端可继续传，但服务端忽略并重算。当前前端不发送该字段。
- **API-015**：GET 在源数据库不可用或格式异常时仍返回日报其他字段，销售摘要为 `source_error` 且金额为 null；POST 不同步执行源查询，始终先按默认金额/已有快照返回成功，后台刷新失败记录错误并保留原快照。水位未追上时 GET 返回 `not_ready`，POST 仍可提交。
- **API-016**：销售摘要状态为 `available`、`not_ready`、`mapping_missing`、`source_error`；历史已提交日报返回 `snapshot`。合法 0 与未就绪/映射缺失/错误分别表达。
- **API-017**：源表水位必须达到 `report_date` 才允许 `available`；未达到日报日或尚未覆盖当月区间时 GET 返回 `not_ready`，POST 按 BR-018 保存计算金额或默认金额，不因未就绪拒绝日报。
- **API-018**：POST 忽略请求体的累计金额，并将按 75% 系数计算和舍入的服务端结果写入 `daily_report.monthly_sales`；日报列表目标完成率继续以该快照为分子。
- **API-019**：`GET /daily/mine?include_sales_summary=false` 只读取日报、目标和身份信息，不等待销售摘要查询；销售摘要通过 `GET /daily/mine/sales-summary` 独立加载。默认 GET 行为保持兼容。

## UI Requirements

- **UI-011**：将累计销售额数字输入控件改为不可编辑的只读金额展示；该字段不再要求用户填写或触发必填校验。
- **UI-012**：自动金额必须用于右侧本月目标完成率、缺口和状态计算；页面显示的金额与进度计算分子一致。
- **UI-013**：可用时展示月初至日报日的区间及源表数据最新日期，金额标注 USD；当源水位未覆盖日报日时不展示来源计算金额，输入区显示默认 `$0.00`。
- **UI-014**：展示加载态；源数据未就绪或无店铺映射时，累计销售额显示为 `$0.00`，并提示提交将采用默认值。已有金额快照在源数据不可用时继续显示。
- **UI-015**：今日日报不因累计销售额未就绪或无店铺映射而禁用提交；其他日期、必填项、合规项和店铺名称数量校验保持有效。销售源数据库或金额格式异常由 API 错误提示处理。
- **UI-016**：查看已提交历史日报时继续显示当时保存的销售额快照；不得在浏览历史记录时静默改写金额。
- **UI-017**：实时自动金额及目标完成率说明明确表示按店铺月累计销售额的 75% 计入；查看历史快照时提示使用当时保存值。

## State Machine

页面销售额读取状态：

```text
loading
  ├─ 有有效映射且 dny_data MAX(rq) >= report_date ─→ available
  │    └─ period_end = report_date
  ├─ 源表水位早于 report_date ─→ not_ready
  ├─ 当前主体没有 dp_ry 店铺映射 ─→ mapping_missing
  └─ 数据库/转换失败 ─→ source_error（日报仍可读取）

available ──提交且服务端复算成功──→ saved_snapshot
not_ready / mapping_missing ──提交──→ 已有快照或默认 0.00
source_error ──不提交──→ 修复源查询错误后重试
```

未就绪或无映射时的新日报按用户确认保存 `$0.00`；销售查询异常仍由接口报告，不静默伪装成零。

## Acceptance Criteria

- **AC-011**：在隔离测试库中给运营 A 分配两家店，准备月初前、月初、日报日、日报日后数据；接口结果等于两店月初至日报日（含）的已批准口径合计，且排除其他运营和区间外行。
- **AC-012**：更改 URL/body 中任何运营 ID 或姓名都不能读取/提交其他运营金额；查询主体始终与有效 JWT `userId` 一致。
- **AC-013**：页面累计销售额无可编辑输入控件，不要求手填；所示金额与完成率计算使用同一个后端金额。
- **AC-014**：请求体提供伪造 `cumulative_sales` 时，保存到 `daily_report.monthly_sales` 的值仍等于服务端复算值；重复提交更新同一 `(operator_id, report_date)` 唯一记录。
- **AC-015**：金额保留两位小数并按 USD 展示；页面同时显示统计区间与源表最新日期。
- **AC-016**：无映射与同步未就绪分别能被识别；新日报仍可提交并将金额保存为 0，更新日报保留已有金额快照；非法数字继续返回错误且不保存。
- **AC-017**：已存在的历史 `daily_report.monthly_sales` 不因读取新接口或部署新版本而批量更改。
- **AC-018**：所有已映射店铺参与计算，不按区域或 `fbs` 过滤；重复 `dpbh` 映射不重复计数。
- **AC-019**：当 `dny_data` 全表 `MAX(rq) < report_date` 时 GET 金额为 null、页面按默认 0 展示，POST 可成功提交；水位达到或超过日报日后，POST 保存月初至日报日的完整区间金额。
- **AC-020**：对日报日 2026-09-30，若全表最新日为 2026-09-30 或更晚，GET 返回 `available`，`period_end` 为 2026-09-30，汇总不包含日报日之后的数据；POST 使用该金额保存快照。
- **AC-021**：对日报日 2026-09-30，若全表最新日为 2026-09-29 或更早，GET 返回 `not_ready` 且金额为 `null`，POST 成功写入默认 `0.00`；若更新既有日报则保留其已有快照。
- **AC-022**：日报日为当月 1 日且源水位仍在上月时，不返回结束日早于月初的可用区间；GET 保持 `not_ready`，POST 仍按 AC-021 规则写入。
- **AC-023**：月累计原值 `14.50` 返回及提交保存为 `10.88`；`1.01 * 0.75 = 0.7575` 按 HALF_UP 舍入为 `0.76`；目标进度与日报列表均以该调整后的金额计算，既有历史快照保持原值。
- **AC-024**：销售摘要查询延迟时，日报/目标基础接口先完成，今日日报表单可操作和提交；摘要在独立请求完成后更新，不影响日期、必填、合规及店铺数量校验。

## Test Cases

- **TEST-011**：服务层月区间边界测试，验证月初前排除、月初/日报日包含、日报日后排除。
- **TEST-012**：权限范围测试，覆盖 `operator`、`leader`、`manager` 的本人主体，确认管理员仍不能提交日报；任何请求参数不能切换主体。
- **TEST-013**：映射测试：多店、其他运营店铺、未映射店铺；重复映射 fixture 不应重复累计同一 `dpbh`。
- **TEST-014**：数值转换测试：两位小数、零、负值/异常文本；异常输入不得静默成为零。负值语义须按业务口径确认。
- **TEST-015**：API 提交测试：客户端缺少或伪造旧金额字段，服务端仍复算，写入并返回保存快照。
- **TEST-016**：重复提交测试：相同运营、日期只有一条日报；第二次提交使用当次复算结果更新快照。
- **TEST-017**：GET 响应契约测试：报告、目标、身份兼容，`sales_summary` 状态/区间/截至日期合法，且无他人数据。
- **TEST-018**：无映射、无源行、源 SQL 异常分别验证返回状态/页面提示及提交策略。
- **TEST-019**：前端测试：累计额不可编辑、自动金额驱动完成率/缺口、loading/error/empty 状态不重叠且无假零值。

## Risks

- **RSK-011**：`dny_data.xse` 无币种/销售定义元数据；错误地按 USD 比较会使目标完成率失真。
- **RSK-012**：`dny_data`/`dp_ry` 关键源列为字符串，映射与店铺/日期组合无唯一约束。`dny_data` 有 `(rq, dpbh)` 非唯一索引，但当前查询和数据增长仍需性能验证；当前样本规则整齐不等于未来数据质量受约束。
- **RSK-013**：源数据观察到最新日期比数据库当前日期早一天。若按当前月动态展示但无截至日期提示，用户可能误判实时性。
- **RSK-014**：当前 3 名启用 `operator` 没有 `dp_ry` 映射；空结果不能自动代表真实零销售额。
- **RSK-015**：源店铺涉及多个 `qy` 和两种 `fbs` 标记；未经确认加过滤会漏算，完全不筛也可能超出业务范围。
- **RSK-016**：当前日报和列表以提交快照计算完成率；若一处用实时值、一处用历史快照，页面指标可能不一致。
- **RSK-017**：公司当前缺少正式集成测试隔离库；禁止用真实业务库写测试日报或测试映射。
- **RSK-018**：同步水位使用 `dny_data` 全表 `MAX(rq)`。这符合当前稀疏日表形态，但无法检测单个店铺相对其他店铺单独晚到；若上游提供批次完成标记，应再评估更精确的同步状态。
- **RSK-019**：`daily_report.monthly_sales` 为 `NOT NULL DEFAULT 0.00`，所以数据未就绪时整份日报提交会暂缓；改变为可空需独立数据库迁移与业务审批。

## Open Questions

- **OQ-011**：`dny_data.xse` 的上游会计定义（例如退款、费用处理）无法从本项目数据库确认；页面按用户确认的 USD 展示，具体财务含义仍为 [NEEDS_CONFIRMATION]。
- **OQ-012**：无单店批次完成标记；当前按全表 `MAX(dny_data.rq)` 判断全局同步水位。若未来要求识别单店迟到需确认上游完整性契约。
- **OQ-013**：[NEEDS_CONFIRMATION] 当前数据库抽样已确认朱文剑的 15 个店铺映射均在 `dny_data` 出现，但没有为所有运营和历史区间验证映射覆盖完整性；若其他账号仍出现缺数，应先用权威店铺清单和源数据批次信息核查，不得用 `fbs_data` 自动补齐。
