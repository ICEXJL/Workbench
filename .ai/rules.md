# AI 工程规则

## 必须遵守

1. 先读 `AGENTS.md`、相关 Spec、README、交接文档和受影响代码，再编辑。
2. 只修改任务范围内的文件；不覆盖、清理或回退用户已有未提交改动。
3. 业务规则不确定时使用 `[NEEDS_CONFIRMATION]`，不得凭经验猜测。
4. 复用现有 API、service、schema、store 和组件；创建新实现前先搜索是否已有同类能力。
5. API 变更必须同步路由契约、前端封装、API 文档、Spec 和测试。
6. 数据库变更必须记录表/字段/索引、兼容策略、迁移顺序、回滚方式和生产风险。
7. 新功能必须有测试；Bug 修复必须有回归测试；测试失败不能被隐藏或降级为“手工确认”。
8. 所有外部输入都要做 schema/参数校验，数据库查询使用参数绑定，错误要有明确 HTTP 状态码和可诊断信息。
9. 权限必须在后端实现；前端菜单隐藏只改善体验，不能作为安全控制。
10. 修改后运行与影响范围匹配的测试、`python -m compileall -q .`、`npm run build` 或 API/浏览器验收，并记录结果。
11. 完成任务前同步文档、Spec 索引、TASK 和 HANDOFF。

## 禁止事项

- 禁止擅自重构无关代码、改目录结构、改命名或批量格式化。
- 禁止删除功能、兼容字段、历史数据处理或用户未提交文件。
- 禁止创建重复的 API、权限判断、日期计算、格式化函数或数据库查询。
- 禁止硬编码数据库地址、密码、JWT 密钥、Token、账号、生产数据或环境特定路径。
- 禁止忽略异常处理、超时、空结果、分页边界、401/403、并发覆盖和数据库连接错误。
- 禁止只改前端而不验证后端授权；禁止只改后端而不更新前端契约和文档。
- 禁止将 PRD 中的目标能力、原型交互或历史验收描述当作当前已实现能力。
- 禁止为了让测试通过修改测试来放宽业务约束，除非 Spec 同步变更并得到确认。
- 禁止在没有迁移/回滚方案的情况下把新 DDL 放进启动流程。

## 安全和数据规则

- `.env`、Token、远程数据库连接信息和真实账号只存在于本地受保护环境。
- 测试使用隔离数据库、mock 或回滚事务；禁止用真实业务库制造验收数据。
- 日志不得打印密码、JWT、完整请求凭据或敏感业务数据。
- 查询范围必须同时考虑 JWT 角色、`operator` 状态、`org_hierarchy` 和 `dp_ry` 映射。
- 任何权限放宽都必须有角色矩阵、越权用例和业务确认。

## 交付规则

任务不能以“代码写完”结束。交付说明必须列出：变更文件、测试命令和结果、文档同步、已知警告、未确认事项和下一步。无法满足 Definition of Done 时，状态写 `partial` 或 `blocked`，不得写 `implemented`。
