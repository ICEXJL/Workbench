# AI 持续开发工作流

本流程适用于本仓库的每次需求、缺陷修复、接口调整、数据库变更和部署说明工作。AI 不得跳过上下文阅读，也不得把未确认的业务假设直接写入代码。

## 标准流程

```text
需求
  → 阅读 AGENTS.md
  → 阅读 README.md、交接文档和相关 SPEC
  → 分析现有代码、依赖、数据流和影响范围
  → 在 tasks/ 创建 TASK
  → 实现最小必要变更
  → 编写/更新测试
  → 运行测试、语法检查和构建
  → 按 Acceptance Criteria 验收
  → 更新 API/数据库/部署文档和 specs/INDEX.md
  → 生成 HANDOFF
```

## 1. 需求

先写清楚目标、用户、范围、非目标、Acceptance Criteria、涉及角色、数据口径和不确定项。无法确认的内容必须写 `[NEEDS_CONFIRMATION]`。

## 2. 阅读上下文

至少阅读：`AGENTS.md`、`README.md`、相关交接文档、相关 `specs/`、受影响的前后端入口、API 封装、数据库查询和已有测试。若任务触及 `.docx` 或原型，只把它们当作需求/设计参考，必须与代码核对。

## 3. 分析与任务记录

在 `tasks/` 创建任务文件，至少记录：

- 任务 ID、日期、目标和非目标。
- 受影响文件、模块、API、数据库表和角色。
- 已确认规则与 `[NEEDS_CONFIRMATION]`。
- Acceptance Criteria、测试计划和回滚策略。

## 4. 实现

采用最小变更原则，复用现有路由、service、schema 和组件边界。禁止为实现局部需求而重构无关模块、复制已有实现、删除兼容字段或改变未确认口径。

## 5. 测试与验收

新功能和 Bug 修复必须增加测试。后端至少执行 `python -m compileall -q .`，前端至少执行 `npm run build`；接口/权限变更还要执行 API 冒烟和越权检查。把命令、结果、警告和未覆盖项写回 TASK。

## 6. 文档同步

API 变化同步 `docs/` 和前端 API 封装；数据库变化同步表/字段/迁移记录；业务规则变化同步 `specs/`；部署变化同步运行说明。更新 `specs/INDEX.md` 的状态，不把历史 PRD 直接标记为已实现。

## 7. HANDOFF

每次任务结束创建或更新 handoff，包含：完成内容、验证命令与结果、未完成项、风险、需要用户确认的业务问题、下一位 AI 的第一步和禁止触碰的用户未提交改动。

## 停止条件

遇到权限口径、数据口径、生产 DDL、真实凭据、外部部署权限或需求冲突时，停止猜测，保留当前安全状态，在 TASK/HANDOFF 中标记阻塞并请求确认。
