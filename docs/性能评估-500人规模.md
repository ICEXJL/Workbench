# 瀛江科技工作台 — 500 人规模性能评估

日期：2026-10-06（含同日对照实验修正）
结论：**瓶颈是数据库的公网往返延迟，不是连接池，也不是进程数。**
本文所有数字均为本机实测，非估算。

## 1. 实测基线

环境：单进程 uvicorn、连接池 `POOL_SIZE=10 + MAX_OVERFLOW=20`（30 连接）、后端与数据库之间为公网链路。

数据规模：`dny_data` 217,415 行 / 1,502 店铺 / 日增约 1,260 行；`dp_ry` 1,479 行；`denglu` 225 账号；`daily_report` 898 行。索引 `idx_dny_rq_dpbh(rq, dpbh)` 已存在。

### 单请求响应时间（admin 全量口径）

| 接口 | HTTP | 耗时 | 响应体 |
| --- | --- | --- | --- |
| `/sales/daily` | 200 | 0.70 s | 27,964 B |
| `/sales/personnel` | 200 | 0.51 s | 19,650 B |
| `/sales/management` | 200 | 0.53 s | 349,782 B |

| `/sales/stats/regional` | 200 | 0.23 s | 1,639 B |

单请求全部在 1 秒内。

## 2. 根因定位：数据库在公网

### 决定性证据

| 测量项 | 数值 |
| --- | --- |
| 数据库地址 | `47.114.36.52:3306`（**公网**） |
| ping RTT | 平均 **21 ms**（20–26 ms，0%丢包） |
| TCP 握手耗时 | **37.6 ms** |
| `SELECT 1` 完整往返 p50 | **57.4 ms** |
| → **单连接理论 QPS 上限** | **17 req/s** |
| → 实测 QPS 天花板 | **约 20 req/s** |

**两者几乎完全吻合。** QPS 天花板由数据库往返延迟决定，与 Python 侧无关。

物理原因：一次最简单的查询也要经历 TCP 握手 + MySQL 认证 + SQL 执行，跨公网至少2–3 个 RTT，累积约 57 ms。而每个 HTTP 请求平均要执行多条 SQL。

### 资源余量充足（证明不是资源问题）

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| CPU 逻辑核心 | 16 | 远未饱和 |
| MySQL `max_connections` | 500 | 上限充足 |
| MySQL 历史峰值连接 | **88** | 只用了 17% |
| `dny_data` 全表扫描 21.7 万行 | 132 ms | 数据库侧轻载 |
| `dny_data` 单日`SUM` | 64 ms | 数据库侧轻载 |

## 3. 三组对照实验（推翻常见直觉）

同一份混合负载压测（权重按真实业务分布构造）：

| 配置 | 50 并发 QPS | 100 并发 QPS | 200 并发 QPS | 200 并发 p95 |
| --- | --- | --- | --- | --- |
| **A** 单进程，30 连接 | 13.1 | 17.3 | 16.0 | 4,810 ms |
| **B** 单进程，**200 连接** | 16.5 | 18.4 | **21.5** | 4,905 ms |
| **C** **4 workers**，每进程 40 连接 | 16.9 | 17.9 | **10.8** | 8,035 ms |

### 结论一：加大连接池几乎没用

连接池从 30 提到 200（6.7 倍），QPS 只从 16.0 到 21.5（**+34%**）。

原因：压测期间连接池开到 200，MySQL 实际峰值连接**只有 44 个**。原来 30 连接的池根本没被用满——**瓶颈不在这里**。

### 结论二：加 workers 反而更慢

4 workers 在 200 并发时 QPS **从 16.0 掉到 10.8**，p95 从 4.8 秒恶化到 8.0 秒。

原因：每个 worker 都要独立走一遍公网往返，而它们争抢的是同一个远端数据库的连接与带宽，且 Windows 下 `spawn` 启动多进程本身有额外开销。**在 I/O 等待型负载（这里是等网络）且共享远端依赖时，多进程不能提升吞吐，反而增加竞争。**

### 结论三：真正的杠杆在减少往返

既然 QPS = 1 / 单请求往返时间，那么**减少每个请求的数据库往返次数**比调连接池、加进程都有效得多：

1. 减少 SQL 条数（接口内多条查询合并）
2. 用 Redis 缓存高频查询结果（尤其 `dp_ry`、`denglu`、月目标这类低频变更的数据）
3. 部署数据库与应用同机房 / 同内网（**这是最大的一项**）

## 4. 500 人场景推算

假设 150 人同时在线（0.3 在线率），前端预取后两页约产生 3 倍请求：

| 指标 | 当前能力 | 需求 | 判断 |
| --- | --- | --- | --- |
| 峰值 QPS | ~20 | ~50 | **不足 2.5 倍** |
| p95 响应 | 4.2–4.8 s | < 1 s | **不达标** |
| 超 2 秒占比 | 47.5% | < 5% | **严重不达标** |

## 5. 优化建议（按实测收益重排优先级）

| 优先级 | 措施 | 实测/预期收益 | 工作量 | 说明 |
| --- | --- | --- | --- | --- |
| **P0** | **部署数据库与应用同内网** | RTT 21ms → <1ms，单连接 QPS 上限可从 17 提升至数百 | 需协调运维 | **唯一能根治的方向**，其余都是缓解 |
| P1 | **Redis 缓存 `dp_ry` / `denglu` / 月目标** | 这些低频变更数据可挡掉大量往返；预计 QPS 提升 2–4倍 | 1天 | 见下方 Redis 说明 |
| P1 | 合并接口内的多条 SQL | 按需减少往返次数 | 半天 | 需逐接口分析 |
| P2 | 连接池提到 50–100 | 实测仅 +34%，但成本极低，可作为辅助 | 改配置 | 顺带做，别指望它救命 |
|~~P2~~ | ~~加 workers~~ | **实测反而更慢，不建议** | — | 仅在应用重启会丢内存状态时才需要 |
| P2 | 压缩 3 个大响应体接口 | 降带宽与序列化开销 | 半天 | `/sales/management` 349 KB、`/report/daily` 267 KB |

### 关于 Redis 到底要不要加

**结论：需要，但不是为了 workers，而是为了缓存。**

- **不是为了多进程限流** —— 因为实测加 workers 会让性能变差，不打算这么部署。限流 Redis 化因此不是当前必需项。
- **是为了减少数据库往返** —— 这是当前唯一的有效杠杆。`dp_ry`（1,479 行店铺映射）、`denglu`（225 个账号）、`target_month`（月目标）变更极少但几乎每个请求都要读，非常适合缓存。

建议：先上 Redis 缓存（第4、5 节 P1），数据库内网化作为中期方案同步推进。

## 6. 容量结论

| 并发规模 | 判断 |
| --- | --- |
| ≤ 20 人 | **可以支撑**，p50 约 1.4 秒 |
| ≤ 50 人 | **勉强可用**，8% 请求超 2 秒 |
| 50–150 人 | **不推荐**，42%–47% 请求超 2 秒，p95 近 5 秒 |
| 150–500 人 | **不可用**，需先完成 P0 与 P1 |

## 7. 已解决的历史问题

**登录限流 IP 维度误伤（2026-10-06 已停用）**：`IP_MAX_ATTEMPTS=30/600s` 在全员共用办公网出口 IP 时会导致任何人输错密码即锁全公司。压测复现：单 IP 300 次尝试触发 274 个 429。现改为 `LOGIN_IP_LIMIT_ENABLED=false` 默认停用，实测单IP 连续 60 次登录全部 401、0 个 429；账号维度（5 次/300 秒/锁 900 秒）保留并实测仍生效。
