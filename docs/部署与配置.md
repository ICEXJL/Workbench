# 部署与配置说明

> 面向对象：在自有服务器（云主机 / 宝塔 / VPS）上部署本系统的运维人员。
> 记录时间：2026-10-10。

---

## 1. 核心结论：系统不会自动识别服务器上的数据库

**这是最容易踩的坑，务必先读。**

`backend/config.py` 的配置读取逻辑是：

```python
DB_HOST = os.getenv("DB_HOST", "127.0.0.1")
DB_USER = os.getenv("DB_USER", "root")
DB_PASS = os.getenv("DB_PASS", "123456")
DB_NAME = os.getenv("DB_NAME", "sales_data")
```

即：**有 `.env` 就用 `.env` 的值，没有才用括号里的默认值。**

而 `backend/.env` 已被 `.gitignore` 排除（`.gitignore` 第 1 行），**不会随代码进入仓库**。

因此 `git clone` 到服务器后，如果不额外配置，系统会尝试连接：

| 配置项 | 会用到的错误默认值 |
| --- | --- |
| 主机 | `127.0.0.1`（本机） |
| 用户 | `root` |
| 密码 | `123456` |
| 库名 | `sales_data`（不存在的中文库名是 `东南亚运营数据`） |

**结果：连不上库，或连上了一个空库。系统不会"自动发现"服务器上的数据库。**

## 2. 环境变量与 .env 的优先级（已实测确认）

`config.py` 第 6-9 行：

```python
load_dotenv(Path(__file__).resolve().parent / ".env")
```

**`python-dotenv` 默认 `override=False`，所以系统环境变量优先级更高。**

实测验证（2026-10-10）：

```
设置 os.environ['DB_HOST'] = 'ENV_VAR_HOST'
load_dotenv('.env') 之后
os.getenv('DB_HOST')  ->  'ENV_VAR_HOST'   # 环境变量胜出
```

这意味着：

- 服务器上用环境变量配置，**会被正确读取**，不必修改任何代码
- `.env` 只起"本地开发默认值"的作用
- 若两者都想改，**以环境变量为准**

> 注：`config.py` 旧注释曾误写为"存在时覆盖环境变量"，实际行为相反，已于 2026-10-10 修正。

## 3. 两种部署方式

### 方式 A：服务器仍连同一远程库（改动最小）

在服务器上创建 `backend/.env`：

```ini
DB_HOST=47.114.36.52
DB_PORT=3306
DB_USER=progress
DB_PASS=<真实密码>
DB_NAME=东南亚运营数据
SECRET_KEY=<至少 32 位随机串>
POOL_SIZE=10
MAX_OVERFLOW=20
```

**缺点**：数据库流量继续绕公网。这正是已实测确认的性能瓶颈根因
（RTT 21 ms，单连接上限约 17 QPS，详见 `性能评估-500人规模.md`）。

### 方式 B：数据库与应用同内网（推荐，同时解决性能问题）

不建 `.env`，直接用系统环境变量：

```bash
export DB_HOST=127.0.0.1      # 或 MySQL 内网地址
export DB_PORT=3306
export DB_USER=progress
export DB_PASS='<真实密码>'
export DB_NAME='东南亚运营数据'
export SECRET_KEY='<至少 32 位随机串>'
python main.py
```

用 systemd 托管时写 `EnvironmentFile=/etc/workbench/workbench.env`，格式为不带 `export` 的 KEY=VALUE。

## 4. SECRET_KEY 必须配置，否则拒绝启动

`config.py` 会做三重校验，任何一项不满足直接抛异常、**进程起不来**：

1. 不能为空
2. 不能是已知弱值（`secret` / `changeme` / `please-change-this-in-production`）
3. 长度 ≥ 32

生成方式：

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

> **注意**：上线后不要更换此密钥，否则已签发的 JWT 会全部失效、所有人被踢回登录页。

## 5. 启动时会对数据库执行 DDL（重要风险）

后端 `main.py` 启动会调用 `database.init_business_tables()`，它会：

| 操作 | 表 | 条件 |
| --- | --- | --- |
| `ALTER TABLE ADD COLUMN` | `denglu` | 缺 `must_change_password` 列时 |
| `ALTER TABLE ADD COLUMN` ×4 | `daily_report` | 缺上涨/下滑店铺相关列时 |
| `CREATE TABLE IF NOT EXISTS` | `operation_security_audit` | 表不存在时 |

**含义：应用账号必须对业务库有 DDL 权限。**

若生产环境使用只读账号，启动时会因权限不足直接**崩溃**，且业务表不会自动创建。

可选做法（当前代码**尚未**实现，需要人工确认后再改）：

- 部署前先由DBA 手工执行这些 DDL，之后再把代码里的检查跳过；或
- 为 `init_business_tables()` 增加环境变量开关（如 `SKIP_DDL_ON_STARTUP=true`）

## 6. 前端部署

前端是静态产物，需要 Nginx（或宝塔）托管：

```bash
cd frontend
npm ci
npm run build        # 产物在 frontend/dist/
```

Nginx 需要把 `/api` 反向代理到后端：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

location / {
    try_files $uri $uri/ /index.html;   # SPA 路由回退，缺这行刷新子页面会404
}
```

**不要遗漏 `try_files`** —— 否则直接访问 `/statsdaily` 这类前端路由时会返回 404。

后端仅供内网访问，不要直接暴露 8000 端口到公网。

## 7. 登录限流在多实例下的限制

`services/login_throttle.py` 的计数存在**进程内存**里。多实例部署（如 gunicorn 开多个 worker、
或后端跑多台机器）时，各进程计数**互不共享**：

- 账号锁定阈值 5 次 / 300 秒 → 单进程内有效，跨进程可能被绕过
- IP 维度已于 2026-10-06 默认停用（`LOGIN_IP_LIMIT_ENABLED=false`）

**要精确控制并发登录次数，必须换成 Redis 等共享存储。**

## 8. 上线前检查清单

- [ ] `SECRET_KEY` 已设为 ≥32 位随机串，且不是示例值
- [ ] `DB_HOST` / `DB_USER` / `DB_PASS` / `DB_NAME` 指向正确的库（**不要留默认值**）
- [ ] 中文库名 `东南亚运营数据` 建议在 MySQL 层建同名的 latin1 别名或改用英文库名，避免各工具编码不一致
- [ ] 应用账号确认具备 DDL 权限，或已手工建好表
- [ ] 8000 端口未直接暴露公网，只经Nginx 转发
- [ ] Nginx 已配 SPA 回退 `try_files`
- [ ] `backend/.env` 未提交进仓库（确认 `git status` 干净）
- [ ] CORS 已按实际域名收紧（`main.py` 内配置）
- [ ] 多实例部署时已评估限流失效风险
