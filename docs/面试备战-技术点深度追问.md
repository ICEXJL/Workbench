## 一、四级权限模型

**可对照代码**：`backend/services/sales_service.py:89-125`（`_scope_clause`）、  
`backend/services/report_service.py:visible_operator_ids`、`backend/routers/auth.py:15-34`（`require_roles`）

### 30 秒版

> 系统有 228 个账号、1487 个店铺，销售额是敏感数据。我做了两层控制：第一层是**接口级角色鉴权**，5 个管理端接口只有 admin 能进；第二层是**数据范围过滤**，按组织架构算出每个人的可见集合。关键点是——角色对不代表数据对，一个组长有查询权限，不代表他该看别的组的数据。

### 3 分钟版

> ***问题****：最初只做了角色校验，但我发现两个漏洞。一是组长能看到全公司数据，二是有人可以通过改请求参数查别人的日报。*
>
> **设计**：我把权限拆成两层。
>
> 第一层是角色。写了一个 `require_roles()` 守卫，作为 FastAPI 的依赖注入挂在路由上。非白名单角色直接 403，并且**在抛异常前先写一条审计记录**，记录账号、角色、访问路径——这样上线后能追溯谁在探权限。
>
> 第二层是数据范围。四个角色四条路径：admin 不加限制；manager 查 `org_hierarchy.manager_id`；leader 查 `leader_id`；operator 只有自己。每层都 `UNION SELECT 自己`——这个必须加，否则本人的数据会漏掉。
>
> **最难的地方在这里**：`dp_ry` 这张店铺归属表里存的是**姓名字符串**，不是 operator_id。所以没法用 id 关联，只能用姓名匹配。而姓名这块历史数据很脏：有 `_W`、`_N` 后缀的主管别名，有停用账号 `夏伊代维护` 这种带「代维护」的，还有 `罗莉娅待维护` 这种占位账号。我做了一层的归一化：查询时用 `REPLACE(TRIM(yy),'代维护','')` 把数据侧的名字清洗掉再匹配；同时在候选集合里把「停用账号的 `_后缀` 变体」也 UNION 进来。
>
> **验证**：我没靠代码审查，用真实账号跑了越权矩阵——12 个接口 × 3 角色，36 项全部符合预期。再验数据是不是真隔离：leader 可见 28 个店铺，必须是 admin 那 1009 个的**严格子集、独有 0 个**。如果只靠前端藏菜单，这个数会是 1009。
>
> **局限**：范围算法在 `sales_service` 和 `report_service` 里各实现了一份，靠文档和测试保证一致，没有抽成一个公共模块。这是个隐患。

### 追问清单

| 追问              | 答法                                                                                     |
| --------------- | -------------------------------------------------------------------------------------- |
| 为什么用姓名不用 id 关联？ | `dp_ry` 是既有业务表，存的是姓名字符串，没有 operator_id 外键。改表结构影响上游 ETL，所以我选择了查询时归一化，而不是改数据源。这是我当时做的取舍。 |
| 姓名重复怎么办？        | 这是真实风险，目前靠人工维护组织表避免。如果重名，两个人的数据会合并计算——这块已知有隐患，正解是给 `dp_ry` 加 operator_id 列。            |
| 前端藏菜单算安全控制吗？    | 不算。前端只做体验优化，真正的边界在后端。我用 curl 绕过前端直接打接口验证过。                                             |
| 怎么防伪造身份？        | 请求体里根本没有 `operator_id` 字段（Pydantic schema 就没定义），后端用 JWT 里的 `userId` 强制覆盖。双保险。          |
| JWT 里放角色安全吗？    | 放了。风险是改了角色要等 token 过期才生效（30 天）。如果要实时生效，得每次请求查库或用 Redis 存角色。这是权衡，我选了性能。                 |
| 越权测试怎么做的？       | 真实账号登录拿 token，然后交叉打接口。断言不能只看「没有 403」，必须校验响应码本身——我踩过坑：本机代理把请求变成 502，但断言只查「没 403」，结果假绿灯。 |
| admin 为什么无限制？   | admin 是管理端，业务上需要看全量。但我加了兜底：admin 不能提交日报（业务规则），防止管理端误操作业务数据。                            |

### 红线

- ❌ 不要说「前后端双重权限控制」——容易被理解成前端也是安全边界
- ✅ 要说「服务端强制鉴权 + 前端体验优化」

## 二、日报销售额状态机

**可对照代码**：`backend/services/report_service.py:94-166`（`get_cumulative_sales`）、  
`backend/routers/reports.py:59-93`、`:110`/`:137`（`BackgroundTasks`）

### 30 秒版

> 填报页要显示「本月累计销售额」，这个数从销售表实时算。但源数据有延迟，直接算会让用户卡在提交按钮上。我的做法是**用状态区分不同原因**，而不是统一报错——没数据就说「还没更新」，店铺没绑定就说「未绑定」，让用户知道该找谁。

### 3 分钟版

> **问题**：日报提交时要带「本月累计销售额」。这个数必须实时算（不能手填，否则可以造假），但源库有延迟，而且运营和店铺的绑定关系可能缺失。
>
> **设计**：我做了个状态机，六个状态，判定有严格顺序：
>
> 1. 先查这个运营名下有店铺吗？没有 → `mapping_missing`（店铺未绑定）
> 2. 源数据最新日期是不是早于填报日？是 → `not_ready`（数据没更新）
> 3. 都满足 → 累加 → `available`
>
> 另外 `snapshot` 是历史快照，`source_error` 是源数据格式异常，`pending` 是待处理。
>
> **有个细节**：计算区间取 `min(填报日, 源数据最新日)`。因为源数据可能只到昨天，那你填今天的时候，累计只能算到昨天——不能因为今天没数据就报错，也不能假装今天有数。
>
> **异步这块**：提交时用 FastAPI 的 `BackgroundTasks` 在后台刷新快照，不阻塞主请求。用户点了提交立刻返回，快照慢慢刷。
>
> **为什么历史用快照**：如果历史日报每次都用实时数据重算，源数据后来被修正了，历史数会跟着变，跟当时报的数字对不上账。所以**提交那一刻把值固化下来**。
>
> **精度**：金额全用 `Decimal` 不用 float，最后一个 `ROUND_HALF_UP` 到两位。用 float 累加会出现 0.01 的误差，财务对账会出问题。

### 追问清单

| 追问                | 答法                                                                          |
| ----------------- | --------------------------------------------------------------------------- |
| 为什么不用定时任务统一刷？     | 定时刷有窗口期，用户刚好在窗口内填就会拿到旧值。按需异步刷是「谁提交刷谁」，更准。                                   |
| 状态为什么不能合并成一个「失败」？ | 因为**处理动作不同**：数据没更新要等，店铺未绑定要找管理员配映射，源数据异常要报技术。合并成一个「失败」用户不知道该做什么。            |
| 异步任务失败了怎么办？       | 主流程已经用当时算出的值存了，快照刷新失败只影响下次展示，不影响这次提交的正确性。                                   |
| 快照和实时会不会不一致？      | 会，这是设计上接受的。历史看快照（当时的账），当天看实时（最新的数）。                                         |
| 源数据日期格式异常怎么处理？    | 抛自定义异常 `CumulativeSalesDataError`，路由层捕获后返回 503 和「累计销售数据暂时无法读取」，不把技术细节暴露给用户。 |
| 累计销售额有系数？为什么？     | 代码里有个 `CUMULATIVE_SALES_FACTOR` 系数。这是业务口径（汇率或统计口径折算），具体数值由业务方定，不是技术随意加减的。   |
| 为什么 admin 不能提交日报？ | 业务规则——管理端只做配置和查看，不参与一线填报，防止数据来源混淆。                                          |

### 加分点

> 「这块最值得说的是：**我一开始想的是技术方案，后来发现真正的难点是业务口径**——比如源数据只到昨天时该显示什么。这类问题代码写不出来，得跟业务方确认。」

## 三、销售查询性能（20 秒 → 0.44 秒）

**可对照代码**：`backend/services/sales_service.py:141-175`（`get_daily_sales`）、`:186-213`（`get_personnel_sales`）

### 30 秒版

> 经营总览原来一次返回全量，20 秒、15MB。我做了两件事：把多次自连接改成一次条件聚合，再加强制分页。结果首屏 0.44 秒、27KB。但后来我测出来，**真正的瓶颈其实是数据库在公网**，不是 SQL 写法。

### 3 分钟版

> **原状**：一次查出所有日期所有店铺，前端再算。数据量 15MB，20 秒。
>
> **优化 1：条件聚合**。原来是按天 join 七次，每次拿一天的数。改成一次扫描，用 `SUM(CASE WHEN rq='某天' THEN 销售额 ELSE 0 END)` 一次出七列。数据库只读一遍数据，不是读七遍。
>
> **优化 2：服务端分页**。原来返回全量让前端截取，现在 `LIMIT/OFFSET` 只拿当前页，总数用单独的 `COUNT` 查。
>
> **结果**：0.44 秒，27KB。
>
> **但我后来做了个对照实验，结论有点打脸**：我把连接池从 30 加到 200，QPS 只涨 34%；开 4 个 worker 进程，QPS 反而从 16 掉到 10.8。这时候我才意识到瓶颈不在应用层。
>
> 我用 `SELECT 1` 测了完整往返，p50 是 57 毫秒。**数据库在公网，RTT 21 毫秒**。这意味着单个连接理论上限就是 17 QPS，怎么调应用层参数都没用。
>
> **所以正确的下一步是数据库和应用同内网**，不是继续抠 SQL 或加进程。

### 追问清单

| 追问                | 答法                                                                         |
| ----------------- | -------------------------------------------------------------------------- |
| 条件聚合和多次 join 的差别？ | join 七次等于扫七遍数据；条件聚合扫一遍出七列。IO 和中间结果集都小一个量级。                                 |
| 为什么加 workers 反而慢？ | 每个进程有自己的连接池。4 个进程等于 4 份连接竞争同一个公网数据库，加上进程间切换开销，反而更差。这个结论是实测出来的，不是猜的。        |
| 索引怎么设计的？          | `dny_data` 建了 `(rq, dpbh)` 联合索引，因为查询都是按日期筛、按店铺关联。                          |
| QPS 只有 20？        | 对，内部系统 228 人，实际并发很低。瓶颈是公网延迟，不是并发能力。**这一点我会主动说，不吹高并发。**                     |
| 现在还能怎么优化？         | 三条：①库和应用同内网（根治）②Redis 缓存低频变更的映射表（`dp_ry`、`denglu`）③合并同一请求里的多条 SQL。第一条收益最大。 |
| 前端做了什么？           | 页缓存 + 预取后两页。但缓存只存在于当前筛选条件下，切换筛选会清空，避免脏数据。                                  |

### 红线

- ❌ 不要说「高并发优化」「支撑几千 QPS」
- ✅ 要说「内部系统并发不高，优化重点是响应时间和传输量；瓶颈定位在数据库网络延迟」

## 四、头程物流多表组装

**可对照代码**：`backend/services/logistics_service.py`（`search_logistics`、`_group_results`、`_attach_container_ocean_quantities`）

### 30 秒版

> 一个 SKU 关联货柜、补货、发货、条码映射四张子表，全是一对多。直接 JOIN 会产生笛卡尔积——3 个柜 × 5 条发货 = 15 行假数据。所以我把五张表**分开查、在服务层用字典按 SKU+仓库分组组装**，不让数据库做这件事。

### 3 分钟版

> **问题**：物流工作台要在一个 SKU 下展示：基本信息、在途货柜（含轨迹）、补货记录、发货记录、条码到柜的映射。五张表全是以 SKU 为键的一对多。如果一条 SQL 全 JOIN，行数会相乘——这不只是性能问题，**是数据正确性问题**，汇总数量会翻倍。
>
> **设计**：分三步。
>
> 第一步，先确定要查哪些 SKU。支持三种输入：精确 SKU、自定义 SKU、产品名模糊匹配。精确匹配优先，模糊匹配最多 20 个，防止一次拉太多。
>
> 第二步，五张表分别按 SKU 列表查。每张表独立查，结果不互相放大。
>
> 第三步，在 Python 里用 `OrderedDict` 按 `SKU → 仓库` 两级分组，把各表数据塞进对应节点。
>
> **有个业务逻辑是在服务层算的**：柜级海运量。要给每个货柜算出「这个柜实际装了多少货」。做法是拿装柜时间，去匹配已发货记录的给货时间——**月日相同、跨年时再看年份**，匹配上的已发货数量求和。这个数在数据库里没有现成的字段，必须每次查询时算。
>
> **排序也是服务层做的**：货柜按「已签收优先 → 日期倒序 → 排序号」三级排，因为已到仓的柜是既成事实，应该比在途的优先展示。

### 追问清单

| 追问                 | 答法                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------- |
| 为什么不在 SQL 里用子查询解决？ | 一对多超过两层，SQL 得嵌套多层子查询或窗口函数。可读性差、改起来容易出错；而单 SKU 粒度数据量很小，Python 组装完全够。**这是拿可维护性换了一点性能**。         |
| 为什么不一次 JOIN 完前端拆分？ | 会笛卡尔积。3 个柜 × 5 条发货 = 15 行，前端还得去重。数据量大时传输也浪费。                                                  |
| 日期怎么匹配的？           | 装柜时间格式很脏，`7.16下午` 这种。我写了个解析器兼容 `YYYY.MM.DD` 和 `MM.DD` 两种，只到月日时用装柜年份推算。跨年情况用「月份小于装柜月份则年份+1」处理。 |
| 怎么判断「已发货」？         | 看 `record_type` 字段，兼容中英文和大小写：`EMITTED`/`SHIPPED`/`已发货`/`已出货`。因为源数据是人工填的，格式不统一。                |
| 有分页吗？              | **没有**。用「单次最多 20 个 SKU」替代。这是当时的取舍——物流查询是按 SKU 精确查，不是列表浏览，20 个足够。如果要做列表浏览得补分页。                 |
| 表名是拼进 SQL 的，安全吗？   | 表名来自代码里的常量白名单元组，不是用户输入。值全部走命名参数绑定，防注入。但**表名位置没法参数化**，这是个潜在风险点，如果以后有动态表名需求必须做白名单校验。            |
| 补货记录为什么只显示近两个月？    | 业务上太久远的补货对当前决策没意义，显示出来只是噪音。                                                                   |
| 为什么关联不到柜的条码不丢掉？    | `link_status` 写成 `UNMATCHED` 但保留数据。丢掉的话，运营会以为这条发货不存在，反而出问题。**宁可显示「未匹配」让人去查，也不能静默丢数据。**        |

### 加分点

> 「物流这块最花时间的地方不是查询，是**数据清洗**——源数据是人工填的 Excel，日期有十几种写法，状态值中英文混着，有的还带 `#N/A` 这种错误值。我的原则是**不猜**：能识别的归一化，识别不了的保留原值并标记出来，不擅自解释。」

## 五、认证与安全

**可对照代码**：`backend/services/login_throttle.py`、`backend/services/audit_service.py`、  
`backend/services/sales_service.py:_password_matches`/`change_password`、`backend/config.py`

### 30 秒版

> 做了五件事：密码用 bcrypt 哈希、JWT 认证、首次登录强制改密、登录失败限流、越权操作审计。其中限流这块我遇到一个真实的坑——**IP 维度限流会误伤全公司**，因为 500 人共用一个出口 IP。

### 3 分钟版

> **密码**：用 bcrypt，cost 12。原来的实现有问题——表里有个 `password` 明文列，部分逻辑还在拿明文比对。我把 220 行明文清零了，只留 `password_hash`，认证只走 `bcrypt.checkpw`。
>
> **JWT**：HS256，密钥做了启动校验——空值、已知弱值、长度小于 32 直接拒绝启动。这个校验救过命：如果不校验，部署时忘了配密钥会用默认值，等于任何人都能伪造任意角色的 token。
>
> **首次改密**：JWT 里带 `mustChangePassword` 标记，`get_current_user` 里检查——如果为 true，除了改密接口，其他接口全部 403。**关键是默认值设成 True**，这样老 token（字段还不存在时发的）也不能绕过。
>
> **限流**：这块是我踩坑最多的地方。
>
> 一开始做了两个维度：账号维度 5 次/5 分钟，IP 维度 30 次/10 分钟。上线前压测发现，**单个 IP 打 300 次登录，触发了 274 个 429**。想一下真实场景：全公司 500 人共用一个办公网出口 IP，任何一个人输错密码都在消耗同一个配额，然后所有人——包括没做错事的人——都收到「登录过于频繁」。这是**误伤**。
>
> 所以我把 IP 维度改成默认停用，只保留账号维度。账号维度已经能防住针对单一账号的暴力破解，而且不影响他人。
>
> **有个细节**：锁定到期时只能清「确实有锁定记录」的计数，不能无差别清。否则未达阈值的失败计数会被误删，导致这个账号永远锁不上。这是我在写的时候发现并修掉的 bug。
>
> **审计**：越权拒绝和登录失败都写 `operation_security_audit` 表。审计写入失败不能影响主流程，所以整个写入包在 try 里吞异常。

### 追问清单

| 追问                       | 答法                                                                                |
| ------------------------ | --------------------------------------------------------------------------------- |
| 限流数据存哪？                  | 进程内存字典，用 `threading.Lock` 保护。**这是已知限制**——多进程部署时各进程计数不共享，能被绕过。要全局一致得换 Redis。       |
| 为什么用 `time.monotonic()`？ | 防止系统时钟被调整（NTP 校准或手动改时间）导致计数错乱。`time.time()` 会受时钟回拨影响。                             |
| 改密后旧 token 还能用吗？         | **能用**，这是当前的设计缺陷。因为 JWT 是无状态的，改密不会让已签发的 token 失效。正解是加 token 版本号或黑名单。目前靠 30 天过期兜底。 |
| 密码复杂度校验了吗？               | 有长度下限，但没做复杂度（大小写+符号）校验。这是可以补的点。                                                   |
| bcrypt cost 12 会不会慢？     | 单次约 250 毫秒，登录场景完全可以接受。而且慢正是它的目的——增加暴力破解成本。                                        |
| 怎么防 SQL 注入？              | 值全部走 SQLAlchemy 的命名参数绑定 `:name`，从不字符串拼接。表名/列名这类标识符没法参数化，靠代码内白名单。                  |
| 审计表会不会爆？                 | 会一直增长，目前没有归档策略。应该有定期清理或分区，这是待办。                                                   |
| 为什么要清明文密码列？              | 明文存储本身是安全事故——一旦库泄露，所有账号直接可用。而且业务上根本不需要存明文。                                        |

### 加分点

> 「限流这块我最大的收获是：**安全策略必须结合真实组织环境**。教科书上 IP 限流是标准做法，但我们公司 500 人共用一个出口 IP，照搬反而把所有人锁在门外。后来我把它改成可选开关，默认关闭，需要时再开。」

## 六、部署（按实际情况选一种说）

### 实情

仓库里**没有 Dockerfile、没有 docker-compose.yml、没有 Nginx 配置文件**。  
线上实例可访问（阿里云），数据库与应用部署在同一台机器的不同端口。

> 注：面试时不要报具体服务器 IP 或端口，说「部署在阿里云」即可。

### 说法 A：如果你实际手动配过服务器

> 「部署是手动做的。前端 `npm run build` 出静态文件，Nginx 托管并把 `/api` 反代到 Uvicorn；后端用 systemd 托管进程。踩过的坑：**SPA 必须配 `try_files` 回退**，否则直接访问 `/statsdaily` 这类子路由会 404；**环境变量优先级**——`python-dotenv` 默认不覆盖已有环境变量，所以生产直接用系统环境变量，不依赖 `.env` 文件。」

### 说法 B：如果部署主要是别人做的（推荐如果你没独立做过）

> 「线上部署目前是团队一起弄的，我主要负责应用侧。部署需要什么我清楚——`SECRET_KEY` 强校验、CORS 白名单、健康检查接口、SPA 回退、环境变量管理——但**容器化这块我还没独立做过**，是我接下来想补的。」

**为什么 B 也不丢分**：老板最怕「说会结果不会」。主动划清边界，前面说的技术点反而更可信。

### 追问清单（无论 A/B 都适用）

| 追问            | 答法                                                                      |
| ------------- | ----------------------------------------------------------------------- |
| 健康检查怎么做的？     | 后端有 `/health` 返回 `{"status":"ok"}`，用来做存活探测和部署后验证。                       |
| CORS 怎么配的？    | 开发环境放开，生产要收窄到实际域名。目前是代码里配置，应该改成环境变量。                                    |
| 密钥怎么管理？       | `SECRET_KEY` 走环境变量，启动时校验长度 ≥32 且不是已知弱值。**上线后不能更换**，换了所有 JWT 失效，所有人被踢出去。 |
| 出故障怎么排查？      | 先看 `/health` 判断是进程挂了还是依赖挂了；再看 Uvicorn 日志的路由和状态码；数据库问题看连接池和慢查询。          |
| 为什么没上 Docker？ | 目前单机部署，没有多环境一致性需求，容器化收益不明显。如果要上多台或频繁换环境，Docker 才有价值。**我不想为了写进简历而上容器。**  |

## 七、通用防守话术

### 被问「这是你一个人做的吗？」

> 「我主导设计和落地，过程中用了 AI 工具提效。但**每个技术选型我都能解释为什么这么做**——比如为什么用姓名而不是 id 做权限关联，为什么把 IP 限流停掉。这些判断是自己做的，不然出了问题没人兜。」

### 被问「最大的技术挑战」

选**限流误伤**或**权限的姓名关联**，因为这两个：

- 有具体的排查过程
- 有反直觉的结论
- 体现了「结合实际环境思考」而不是套模板

### 被问「如果重做会怎么改」

> 「三件事：第一，先把权限的姓名关联改成 id 关联，从数据源头解决，而不是查询时打补丁；第二，范围算法抽成一个公共模块，现在两处各写一份，靠测试保证一致太脆弱；第三，把数据库和应用放同内网，这是性能的根治办法。」

### 别碰的三句话


| 别说 | 原因 |
| --- | --- |
| 「高并发」「海量数据」 | 真实规模撑不住追问 |
| 「前后端双重权限控制」 | 暗示前端是安全边界，技术上不成立 |
| 「9 个月顶别人两年」 | 空话，反而减分 |
