# T14 · RBAC 权限体系核查（2026-10-06）

## 背景

用户提问「RBAC 权限体系现在做好了吗？做好权限限制了吗」。此前文档记录 RBAC「已实现」，
但四角色端到端验收中 manager 角色一直没有实测记录，日报列表范围也从未实测过。
本次用真实账号做完整核查，不采信代码审查结论。

## 验收标准

1. 12 个业务接口 × admin/leader/manager 三角色的返回码符合角色预期
2. 数据范围真实隔离（店铺、人员、日报三层）
3. 越权专项：无 Token、伪造 Token、伪造 operator_id、越权读目标均被拦下
4. 审计日志真实落库
5. manager 角色补做端到端验收
6. 关键权限逻辑固化为可回归的自动化测试

### 二、数据范围隔离（这是权限是否真落地的关键）

| 维度 | admin | leader | manager | 隔离结论 |
| --- | --- | --- | --- | --- |
| 可见店铺（/sales/daily） | 1009 家 | 28 家 | 181 家 | leader 是 admin 严格子集，独有 0 家 |
| 可见人员（/report/people） | 224 人 | 3 人 | 40 人 | leader 是 admin 子集 |
| 日报记录（/report/daily 10-01~10-06） | 448 条 / 224 人 | 6 条 / 3 人 | 80 条 / 40 人 | leader 涉及人员是 admin 子集 |

**结论：范围过滤真实生效，不是靠前端隐藏。**

### 三、越权专项

| 攻击尝试 | 结果 | 拦下机制 |
| --- | --- | --- |
| 无 Token 访问业务接口 | 401 | `get_current_user` |
| 伪造 Bearer Token | 401 | JWT 签名校验 |
| leader 指定范围外 operator_id 读日报 | 200 但 **0 条** | `list_reports` 把 ids 收窄为空 |
| manager 指定范围外 operator_id 读日报 | 200 但 **0 条** | 同上 |
| leader/manager 读他人月目标 | **403** | 显式 `not in visible_operator_ids` |
| leader/manager 写月目标 | **403** | `role != "admin"` |
| 请求体携带 `operator_id=1` 提交日报 | 落库为提交者本人 156 | schema 无该字段 + `save_report` 强制覆盖 |
| 无 Token / 无登录态调用管理端接口 | 403 | 双层 |

**身份防伪造是双保险**：`DailyReportPayload` 根本没有 `operator_id` 字段（Pydantic 默认忽略多余字段），
且 `save_report` 执行 `data = {**payload, "operator_id": int(user["userId"])}`强制覆盖。

## 遗留缺口（未做，需决策）

1. **日报详情/删除接口缺失** —— 目前只能靠列表接口的 operator_id 过滤做范围控制，
   没有独立的「按 id 读单条日报」接口，因此不存在该接口的越权面；
   但未来若新增详情接口，必须复用 `visible_operator_ids` 校验。
2. **范围变更无自动化测试基线** —— `org_hierarchy` 表是范围的唯一依据，
   但没有测试覆盖「某人被调组后其leader 看到的范围随之变化」。
3. **无 CI** —— 42 项测试目前只能手动跑。
4. **管理端接口仍缺 service 层范围参数** —— `sales/stats/*` 与 `sales/distribution/*`
   目前靠 `require_roles("admin")` 整块拦住，非 admin 无法进入，因此当前无泄露；
   但若将来放开给 leader 看区域数据，必须先给 service 补范围参数，不能只摘 admin_only。
