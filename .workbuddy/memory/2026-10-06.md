## 500 人规模性能评估（同日 14:51后）

产物：`docs/性能评估-500人规模.md`，提交 `31e03be`。README 已同步规模限制。

### 结论：当前配置支撑不了 500 人，QPS 天花板约 20

单请求全部 <1s（`/sales/daily` 0.70s 最慢），**但并发一压就崩**。

混合负载实测（按真实业务分布构造）：

| 并发 | 墙钟 | QPS | p50 | p95 | 超2秒 |
|---|---|---|---|---|---|
| 20 | 1.64s | 12.2 | 1.379s | 1.634s | 0% |
| 50 | 2.43s | 20.5 | 1.302s | 2.122s | 8% |
| 100 | 5.66s | 17.7 | 1.800s | 4.787s | **42%** |
| 200 | 9.74s | 20.5 | 1.872s | 4.223s | **47.5%** |

**从 50 并发起QPS 就封顶，之后加压只增加排队。**

### 瓶颈不在数据库（有决定性证据）

SQL 层单独执行：全表扫 21.7万行 132ms、单日 SUM 64ms、7日聚合 194ms —— 都不是问题。

**决定性证据**：`/report/people` 的 SQL 只要约 5ms，压测下并发 20→ QPS 26.4 / p50 432ms，
并发 120 → QPS 67 / **p50 726ms**。时间全耗在SQL 之外。

根因三条（代码事实）：
1. `backend/main.py:37` `uvicorn.run(app, ...)` **无 workers** → 单进程
2. 所有路由是同步 `def`（非 `async def`）→ 走 anyio 线程池（上限 40）排队
3. `config.py:24-25` `POOL_SIZE=10 + MAX_OVERFLOW=20` = 30 连接

### 发现上线必修的隐蔽问题：IP 限流会误伤全公司

压测 300 次登录尝试 → **274 个 429 / 26 个 401**（`IP_MAX_ATTEMPTS=30/600秒`）。

### 关键推论

加 workers 会让限流失效——`_account_failures`/`_ip_attempts` 是进程内 dict，
4 个 worker = 4 份独立计数，攻击者可用 4 倍配额绕过。**必须成对改造，不能只加 workers。**

数据增长：日增约 1260 行，一年约 67.7 万行，MySQL 轻载，暂不需要分区/归档。

容量分档：≤20 人可支撑 / ≤50 勉强可用 / 50-150 不推荐 / 150-500 不可用。

## 停用登录限流 IP 维度（同日 15:10 后）

提交 `8b042ec`。用户同意我的判断：「这确实是一个问题」。

### 实现方式：停用而非删除

`services/login_throttle.py` 新增开关，**保留原实现**：

```python
IP_LIMIT_ENABLED = os.getenv("LOGIN_IP_LIMIT_ENABLED", "false").lower() in ("1","true","yes")
```

停用时 `is_ip_blocked()` 恒返回 False，`register_ip_attempt()` 直接 return，
不产生任何状态。将来若需防批量枚举账号，设 `LOGIN_IP_LIMIT_ENABLED=true` 即可恢复。

`routers/auth.py` 改为 `if login_throttle.IP_LIMIT_ENABLED:` 才读取 `request.client`
—— 停用时连客户端 IP 都不取，省掉一次属性访问。

**保留账号维度**（5 次/300 秒/锁 900 秒），防单一账号暴力破解。

### 实测验证（重启后端后的真实 HTTP，非单测）

- 单 IP 连续 60 次错误登录 → **全部 401，0 个 429**（改前 30 次后就开始 429）
- 同一账号连续 8 次 → 1-5 次 401，**第 6 次起 429 + 剩余秒数**（账号维度未被误伤）
- admin 登录 200 + `/auth/me` 200 role=admin
- 浏览器实测：错误密码显示「账号或密码错误」而非 IP 限流提示
- unittest 24 项全绿（IP 测试从 3 项重写为 5 项，覆盖停用/启用两种状态），compileall 通过

### 踩坑（重要，下次直接套用）

1. **本机系统代理会污染 localhost 请求**：`http_proxy=127.0.0.1:56975` 导致
   Python/urllib 访问 127.0.0.1:8000 走代理 → 返回 502 `upstream connect failed`。
   curl 要加 `--noproxy '*'`（但 Git Bash 下 `--noproxy` 也不可靠，**用 Python 更稳**）。
   验证前必须 `unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY`。
2. **假通过陷阱**：第一次验证时 curl 和 Python 全部拿到 502，脚本却输出
   「通过：0 个 429」——因为 502 本来就没有 429。**断言必须校验响应码本身是 401/200，
   不能只校验「没有 429」**。这个坑让我差点交上一个假的绿灯。
3. **后端用 `&` 起会随命令结束被回收**：必须用 Bash 工具的 `run_in_background=true`。
   症状是验证跑出 123 秒（全是代理重试）+ WinError 10061。
4. **沙箱会 SIGTERM 掉含复杂内容的 `python -c`**：写成 `.py` 文件再跑就正常。
   `/auth/me` 返回的是 `sub` 不是 `username`（我一开始写错报KeyError）。

## 性能根因修正：数据库在公网（同日15:33 后）

用户追问「连接池上调到 100 能解决吗，workers 是什么意思，要加 Redis 吗」。
我做了三组对照实验，**推翻了自己此前「加 workers」的结论**。

| 配置 | 50并发 QPS | 100并发 | 200并发 QPS | 200并发 p95 |
|---|---|---|---|---|
| A 单进程 30 连接 | 13.1 | 17.3 | 16.0 | 4810ms |
| B 单进程 **200 连接** | 16.5 | 18.4 | **21.5** | 4905ms |
| C **4 workers** | 16.9 | 17.9 | **10.8** | **8035ms** |

### 真正根因：数据库在公网

- 数据库 `47.114.36.52:3306`，**ping RTT 21ms**，TCP 握手 37.6ms
- `SELECT 1` 完整往返 p50 = **57.4ms** → 单连接理论上限 **17 QPS**
- 实测天花板约 20 QPS —— **两者吻合，QPS 由网络往返决定**

### 关键否证

- 池开到 200（6.7 倍）只+34%，且压测中 MySQL 峰值连接**仅 44**（原 30 池根本没吃满）
- CPU 16 核远未饱和；MySQL `max_connections=500` 没用满
- **4 workers 反而更慢**：I/O 等待型负载 + 共享远端 DB = 多进程只增加竞争；
  Windows `spawn` 还有额外开销

**教训**：看到「单进程」就默认该加 workers，是错的。必须先定位瓶颈类型——
CPU 密集才加进程，I/O 等待应该减少往返次数。

### Redis 的定位（与此前说法不同）

需要，但**不是为了多进程限流**——既然实测不加 workers，就不必 Redis 化限流。
是为了**缓存减少数据库往返**：`dp_ry`(1479 行) / `denglu`(225 账号) / `target_month`
这类低频变更、几乎每请求都读的数据。

### 优先级重排

1. **P0 数据库与应用同内网**（RTT 21ms→<1ms，唯一根治方向）
2. P1 Redis 缓存 + 合并 SQL（预计 QPS 提升 2–4 倍）
3. P2 连接池提 50–100（顺手做，+34%）
4. ~~加 workers~~ **实测更慢，不做**
